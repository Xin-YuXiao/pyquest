# JSDoc 类型检查渐进引入

Status: needs-triage
Priority: P3
Source: 接手评估新增。项目是纯 JS，没有任何类型检查；已有的 PropDef / Interactable 两个 JSDoc typedef 只是文档，且已经和代码对不上（见备注）
Depends on: 无（若 `core-unit-tests` 已落地，core 层分批时可顺带受益，但不阻塞）

## 问题陈述

PyQuest 有约 7600 行 JS，分为数据层（章节注册表、地图构建器、题库）、core 层（全局状态、存档、章内阶段、抽题、测试接缝）、ui 层（DOM 覆盖层）以及 scenes/entities（Phaser 场景与实体）。各层之间靠一些隐含的数据契约连接：

- 章节配置对象有几十个字段（主题、题池映射、NPC 台词表、胜利文案等），有的可选，有的是「数组或函数」两种形态。
- 地图道具描述（PropDef）被场景消费后转成可交互对象（Interactable）。
- 存档 JSON 的结构必须与全局状态 G 对应，而且存档 v3 即将改动它。
- 题目对象有 9 个字段，其中填空、BOSS 标记是可选的。

这些契约只存在于注释和作者的记忆里，没有任何工具检查。后果已经出现：现有 PropDef typedef 把解锁条件写成字符串数组，实际所有地图传的都是 { 章, 标志 } 对象或函数，文档与代码早已背离而无人知晓。接下来存档 v3、新题型、新章节都会改动这些契约，没有类型检查，就只能靠 E2E 在运行时撞出来。

## 解决方案

用 TypeScript 编译器只做检查（不产出代码），对 JS 文件读取 JSDoc 类型注解，渐进式引入：

- 先建好基建：检查命令接入 `npm run check` 与 CI，初始时不检查任何文件，因此零报错。
- 按层分批开启：数据层 → core 层 → ui 层 → scenes/entities。每批为该层补上关键 typedef（题目、题池、章节配置、地图定义、存档结构、全局状态）并修掉报出的问题，CI 随之覆盖到这一层。
- 全部完成后收口：改为全局开启，删除逐层开关。

全程不改成 .ts 文件，不引入构建步骤变化，运行时行为零变化。

## 用户故事

1. 作为维护者，我想要章节配置写错字段名或类型时在 CI 里就报错，以便不用等 E2E 跑到那一章才发现。
2. 作为维护者，我想要题目对象缺字段、类型不对时被类型检查发现，以便题库扩充时多一道防线。
3. 作为维护者，我想要存档结构和全局状态 G 有明确的类型定义，以便存档 v3 改动时编译器帮我找出所有受影响的读写点。
4. 作为维护者，我想要编辑器能根据 JSDoc 给出补全和悬停提示，以便读章节配置时知道每个字段的含义。
5. 作为维护者，我想要类型检查一层一层地开启，以便每次只处理一层的报错，不会一下子冒出几百个错误。
6. 作为维护者，我想要还没开启的层不影响 CI，以便渐进过程中主干始终是绿的。
7. 作为维护者，我想要每批开启时修掉的问题都分清「真 bug」和「仅类型标注」两类，以便真 bug 单独评审。
8. 作为维护者，我想要 Phaser 对象（场景、精灵、物理体）都有官方类型提示，以便场景代码调用 Phaser API 时不拼错方法名。
9. 作为维护者，我想要 DOM 查询结果可能为空的地方被类型系统提醒，以便页面结构改动时不出现空引用。
10. 作为维护者，我想要现有 PropDef / Interactable typedef 被修正为与代码一致，并由检查器强制约束，以便文档不再撒谎。
11. 作为维护者，我想要题型扩展（新题型）有可区分的联合类型，以便新增题型时编译器指出所有需要处理的分支。
12. 作为新加入的贡献者，我想要通过类型定义读懂各层之间的数据契约，以便上手更快。
13. 作为维护者，我想要类型检查足够快（本机数秒内），以便能放进 `npm run check` 日常运行。
14. 作为维护者，我想要类型检查与 ESLint 分工明确、不重复报同一个问题，以便输出不嘈杂。
15. 作为维护者，我想要「临时忽略某行类型错误」必须写明原因，以便忽略不会被滥用。
16. 作为维护者，我想要收口之后全局开启检查，新文件默认就被检查，以便不会出现漏网的新代码。
17. 作为 E2E 维护者，我想要测试接缝暴露的查询与动作也有类型，以便测试脚本调用接缝时不传错参数。

## 实现决策

- **工具**：TypeScript 编译器，只做检查、不产出（noEmit），开启 allowJs 与 checkJs，并启用 strict 族选项中性价比高的部分。起步建议：先开 strictNullChecks 与 noImplicitAny，逐层评估后再决定是否全开 strict。
- **TypeScript 版本**：npm 当前最新版是 7.0.x（原生实现）。JSDoc / checkJs 在 7.x 中的支持程度需核实。推荐先用 6.0.x 或 5.9.x 这类对 JSDoc 支持久经验证的版本，并锁定版本号；7.x 的 JS 检查成熟后再升级，升级本身单独做一张工单。
- **expand–contract 分批**：
  - **expand**：一个检查配置，包含列表初始为空，先接入 `npm run typecheck` 与 CI。
  - **migrate**：每批把一层加入包含列表，补 typedef 并修错：数据层 → core → ui → scenes/entities。
  - **contract**：改为全局包含 src，删除分批列表。
- **共享类型定义**：新建一个只放 JSDoc typedef 的类型模块，按领域组织：题目（Question）、题池（Pool）、章节配置（ChapterDef，含主题、题池映射、台词表）、地图定义（MapDef 与 PropDef）、可交互对象（Interactable）、章进度（ChapterProgress）、全局状态（GameState）、存档 v2（SaveV2）。现有 PropDef / Interactable 从场景文件迁入并修正：解锁条件的类型改为「{ 章, 标志 } 对象或以全局状态为参数的函数」。
- **题目类型用可区分联合**：四选一题与填空题以 fill 字段区分，为 `pyodide-sandbox` 将来的新题型（代码题等）预留可扩展的判别字段。若届时题型分派 prefactor（`../pyodide-sandbox/issues/01`）已经引入了 kind 字段，以它为准。
- **Phaser**：使用 Phaser 包自带的类型声明（随 npm 包提供，无需额外安装类型包）。
- **忽略规则**：只允许「期望出错」类注释，并且必须附原因；用一条 ESLint 规则或 grep 检查来强制附原因。
- **与 ESLint 分工**：ESLint 管代码坏味道（未用变量等），类型检查管契约。两者重复的规则（如未定义变量）以 ESLint 为准，类型检查不额外开同类选项。
- **不改运行时**：每批改动只能是 JSDoc 注释和为满足类型而做的等价改写。若发现真 bug，单独提交并在提交说明里标注，不与类型标注混在一起。

## 测试决策

- 类型检查本身就是测试，验收方式是「该批目录在检查范围内且零报错」。
- 每批完成后跑一次 `npm run check`（lint、单元、smoke、verify、build、E2E），证明运行时行为零变化。
- **先例**：现有 PropDef / Interactable typedef（场景基类文件里）是 JSDoc 风格的先例；ESLint flat config 的「先接入、后修问题」节奏是渐进引入的先例。

## 待决策

1. **TypeScript 版本**：推荐锁定 6.0.x（或 5.9.x），理由是对 JSDoc 的支持成熟。7.x 原生版对 JS 检查的支持需核实后再定。
2. **strict 程度**：推荐分两步，先开 strictNullChecks 与 noImplicitAny，收口后再评估是否全开 strict（全开后 Phaser 回调的 this 类型等会带来大量标注成本）。
3. **测试脚本（scripts/）是否纳入检查**：推荐不纳入，至少第一阶段不纳入。E2E 脚本里有大量在浏览器里执行的回调，类型化收益低。

## 不做的事

- 不把任何文件改成 .ts，也不改变构建链。
- 不追求 100% 类型覆盖；第三方回调、Phaser 动态属性允许宽松标注。
- 不在这个 effort 里重构代码结构。

## 备注

- 现状核实：全仓库 JSDoc 注解几乎都集中在场景基类的两个 typedef 里。PropDef 把 requires 标为字符串数组，而地图构建器里所有封印门、传送门传的都是 { ch, flag } 对象（状态模块的解锁解析也支持函数形式）。这正是没有类型检查时文档会悄悄背离代码的实例。
- 规模：数据层约 3800 行（题库就占 2700 行，几乎全是字面量数据，检查成本低）；core 约 490 行；ui 约 1300 行；scenes/entities/textures/audio 约 1900 行。
