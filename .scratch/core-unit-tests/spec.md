# 核心逻辑单元测试层

Status: needs-triage
Priority: P0
Source: 接手评估新增。核心规则（章内阶段、抽题、存档迁移、解锁条件）现在只靠 smoke 大脚本和约 8 分钟的全章节 E2E 间接覆盖；存档读写与 v1→v2 迁移完全没有自动测试；即将到来的存档 v3（见 `learning-records`）需要一个能写迁移测试的地方
Depends on: 无

## 问题陈述

PyQuest 的核心规则集中在几个纯逻辑模块里：全局状态与解锁条件、章内阶段推断、抽题、存档。目前它们的测试情况是：

- **smoke** 是一个顺序执行的大脚本，直接改写全局状态 G 来测抽题行为。它擅长「用真实全量数据做完整性扫描」，但不适合表达边界规则。例如「题池全部答完后允许复用」「其他符文石已抽走的题要避开」这类情况，要么没测，要么和前面的步骤共享状态、互相干扰。
- **E2E** 覆盖真实路径，但跑完 11 章约 8 分钟，失败时定位到具体规则很费劲。
- **存档模块完全没有测试**：v1→v2 迁移把旧字段映射到第一、二章进度，损坏 JSON、版本不符、隐私模式下 localStorage 抛异常等分支，都没有任何自动验证。下一步 `learning-records` 要引入存档 v3，迁移链会变成 v1→v2→v3，没有测试层，这是数据丢失风险最高的改动。
- **两份重复实现**：「继续冒险」落点有两份实现，`saveChapter` 读原始存档计算、`furthestChapter` 读内存状态计算，规则相同、代码各写一遍。目前没有任何东西保证两者一致。

## 解决方案

引入轻量的单元测试层（vitest，DOM 相关部分用 happy-dom 模拟），接入 `npm test` 与 CI，先覆盖四块核心规则：章内阶段、抽题、存档与迁移、解锁条件与落点。与 smoke 分工明确：

- **smoke**：用真实全量数据做完整性扫描（全部地图能构建、全部题池有效、全部符文槽映射正确）。
- **单元测试**：用受控状态精确表达规则与边界（某种状态下必须得到某种结果）。
- **E2E**：验证玩家可见的端到端流程。

## 实现决策

- **工具**：vitest，作为开发依赖。存档、状态等模块会访问 document 事件和 localStorage，这些测试运行在 happy-dom 环境中；纯逻辑测试运行在 node 环境中。测试文件显式导入断言函数，不开全局注入，与 ESLint 的 recommended 配置保持一致。
- **接入方式**：`npm test` 依次运行 smoke → 单元测试 → verify-quiz。若 `quiz-bank-lint` 已落地，其 lint 步骤排在 smoke 之后。CI 沿用 `npm test` 步骤，工作流文件不用改。`npm run check` 不变。
- **测试位置与命名**：测试与被测模块按领域对应，命名直接用领域术语（例如「章内阶段」「抽题」「存档迁移」），便于对照 GLOSSARY。
- **状态隔离**：每个测试前调用状态模块已有的重置函数，并清空模拟的 localStorage。抽题测试中的随机数通过替身固定，确保结果确定。
- **不为测试改生产代码的结构**：抽题直接使用真实题库数据，挑一个题量小的真实题池（如 W1 BOSS 池，4 题）来构造「耗尽」场景，不引入依赖注入。若某条规则确实无法在不改结构的前提下测试，就在该工单 Comments 记录，并建 prefactor 工单，不顺手重构。
- **存档测试夹具**：提供构造 v1 存档、v2 存档的工具函数（返回原始 JSON），供本 effort 与 `learning-records` 共用。
- **一致性属性测试**：随机生成各章完成状态组合，先写档，再分别用「读原始存档」和「读内存状态」两条路径计算「继续冒险」落点，断言结果相同。
- **覆盖率**：先报告、不设门槛（vitest 自带 v8 覆盖率），范围限定为核心模块。是否设门槛另行决定。

## 测试决策

- 好测试只验证模块对外的可观察行为：函数返回值、全局状态变化、存档内容、发出的事件。不断言内部变量，也不断言调用顺序。
- **测哪些模块**：章内阶段（含 NPC 台词选择）、抽题、存档（保存/读取/迁移/清除/落点探测）、全局状态的解锁条件解析与落点计算。
- **不测**：渲染、场景、实体（继续由 E2E 覆盖）；题库数据完整性（继续由 smoke 和题库 lint 覆盖）。
- **先例**：smoke 第 [3e] 段已经演示了如何直接操作 G 并调用抽题函数，单元测试沿用同样的调用方式，只是拆成彼此隔离的用例。
- **与 smoke 的关系**：smoke 的抽题抽样检查保留（它在全部 248 个符文槽上跑真实数据，是另一个维度的保障）。单元测试补充 smoke 不擅长的边界情况。

## 待决策

1. **测试框架**：推荐 vitest。它与现有 Vite 构建链同源，配置成本最低，并原生支持 ESM。备选是 Node 内置测试运行器：零依赖，但 DOM 模拟和覆盖率都要自己拼。
2. **DOM 模拟库**：推荐 happy-dom。它比 jsdom 轻、启动快，而这里只用到 localStorage、document 事件和 CustomEvent。
3. **是否设覆盖率门槛**：推荐第一阶段只报告，等存档 v3 落地后再按核心模块设门槛，避免一开始就为凑覆盖率写低价值测试。

## 不做的事

- 不重写或删减 smoke。
- 不给场景、实体、UI 写单元测试。
- 不为了可测性重构生产代码（确有需要时另建 prefactor 工单）。
- 不引入快照测试。

## 备注

- 现状核实：`saveChapter`（存档模块，读原始 JSON）和 `furthestChapter`（状态模块，读 G）实现了同一条落点规则：第一章未通关落在 1，否则落在「最后一个已通关章 + 1」，并以章节总数为上限。
- 存档模块对 localStorage 的每次访问都包在 try/catch 中，静默失败。测试要覆盖「抛异常时不影响游戏」这一契约。
- `learning-records/issues/01`（存档 v3）依赖本 effort 的 01；最好把存档测试夹具（本 effort 的 03）也先做完。
