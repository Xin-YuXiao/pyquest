# 找 bug 符文：先定位、再修复，用测试说话

Status: needs-triage
Priority: P2
Source: 接手评估新增 · 借鉴教学研究（见 .scratch/INSPIRATION.md）——Gidget（debugging-first 教学游戏）与 Pyzzles（最少改动即最佳修复）
Depends on: pyodide-sandbox（硬依赖其 01 号题型分派扩展点；可选复用其沙盒运行测试）；协同 vibe-coding-dialogue（同为第十章题型，避免情景重复）、learning-records（作答记录）

## 问题陈述

- 学生写的代码大部分时间是「有 bug 的」，而课程和游戏都在练「读正确代码、猜输出」，从没练过**调试**：
  看到测试红了 → 找出哪一行错 → 想清楚怎么改 → 确认测试转绿。
- 第十章「灵思之塔」要教的核心正是「AI 给的代码看起来对，但要靠测试验证」。现在的 W10 题（vc11 漏归一化、
  vc12 角度当弧度、vc13 bin 边界 off-by-one、vc15 除零污染、vc16 math 遇数组）都把 bug **直接摆在题面上**让人挑，
  真实场景里 bug 是藏着的，需要学生自己去**找**。
- vc20 讲「旧测试变红时不能改期望值迁就输出」，但学生从没真的面对过一个「把测试改掉就能变绿」的诱惑。
- Gidget 的研究提示 debugging-first 是一条有效路径：目标写成测试用例，学习者检查、修改、测试既有代码；
  对照研究中学习收益与常规教程相当、用时约一半（见备注）。

## 解决方案

新增题型「找 bug」（`kind: 'debug'`），两步完成：

1. **看测试**：面板上方是一段「AI 生成的」代码，下方是测试表：每条测试的「期望」与「实际」（实际值由构建期真实运行得出，红色 ✗ 标出不符的）。
2. **第一步·定位**：点出（或键盘选中）你认为出错的那一行。点错不扣心，但给一句方向性提示（「这一行的计算和测试无关，看看结果是在哪里算出来的」）。
3. **第二步·修复**：定位正确后，出现 3-4 个候选修复（替换这一行 / 改测试期望值 / 其他看似合理的改法），选一个提交。
4. 选对：测试表全部转绿（预先算好的「修复后实际值」），发奖励、显示解析；
   选错：扣 1 心，显示「用这个修复后，第 N 条测试的实际值会是 X」——让学生看到错误修复的后果。
5. 候选修复里固定有一个「把测试期望值改成实际输出」的作弊选项，选它判错并点名：「测试没错，错的是代码」（与 vc20 呼应）。

## 用户故事

1. 作为 W10 学生，我想看到一段带测试的「AI 代码」并亲手找出 bug，以便练习「先验证再信任」而不只是背口诀。
2. 作为学生，我想测试表同时显示期望和实际，以便从差异推断 bug 的位置。
3. 作为学生，我想先定位出错的行，再选修复，以便把「找 bug」和「改 bug」分开练。
4. 作为学生，我想定位错时得到方向性提示而不是直接扣心，以便敢于尝试推理。
5. 作为学生，我想选错修复时看到这个修复会让哪条测试仍然失败、实际值是多少，以便理解为什么它不对。
6. 作为学生，我想选对修复后看到所有测试转绿，以便获得「修好了」的确定感。
7. 作为学生，我想在候选里遇到「改测试期望值」这种作弊选项并被点名，以便记住「测试是需求的可执行形式」。
8. 作为学生，我想修复以「只改一行」的形式呈现，以便关注最小、最精确的修改。
9. 作为只用键盘的学生，我想用 ↑/↓ 选行、Enter 确认定位、1-4 选修复，以便不用鼠标。
10. 作为触屏学生，我想直接点代码行定位，以便在平板上也能玩。
11. 作为学生，我想答对后看到解析（这个 bug 为什么常见、怎么在测试里拦住它），以便把一次修复变成一条经验。
12. 作为色弱学生，我想测试结果的 ✓ / ✗ 有符号和文字，不只靠红绿，以便看得清。
13. 作为教师，我想找 bug 题由已审核的 W10 情景改编，改编稿经助教确认后才上线，以便内容符合 ADR-0001。
14. 作为教师，我想在作答记录里分别看到「定位尝试次数」和「修复是否一次选对」，以便区分「找不到 bug」和「不会修」。
15. 作为助教，我想课上能用同一道找 bug 题现场演示调试思路，以便复用游戏内容。
16. 作为内容作者，我想只写「有 bug 的代码 + 测试 + 正确修复 + 候选修复」，测试的实际值由构建期自动跑出，以便不手算任何数字。
17. 作为内容作者，我想构建期校验自动保证：有 bug 的代码至少一条测试失败、正确修复全部通过、每个错误修复至少一条失败，以便题目逻辑严密。
18. 作为内容作者，我想「改测试期望值」类候选被显式标记为作弊选项，校验器对它跳过「必须失败」的检查，以便表达这类教学意图。
19. 作为维护者，我想找 bug 题复用题型分派扩展点，以便不改答题面板公共外壳。
20. 作为维护者，我想找 bug 题放在独立题池与独立槽位，以便不影响现有 W10 题池的抽题与 tier。
21. 作为 E2E 维护者，我想接缝能读到「正确行号」和「正确修复下标」，以便测试用真实点击完成两步作答。
22. 作为后续维护者，我想沙盒（pyodide-sandbox）落地后，「运行测试」可以从预计算切换为真跑，以便以后支持更开放的修复。

## 实现决策

- **题型**：`kind: 'debug'`，经 pyodide-sandbox 01 号题型分派注册渲染器；渲染器自己处理键盘（↑/↓ 选行、Enter 定位、1-4 选修复），
  声明 `keyboardShortcuts: false` 以免与外壳的 1-4 快捷键重复触发。
- **数据契约**（极简形状）：
  ```
  {
    kind: 'debug', chapter, tier, prompt, explain,
    from: 'vc11',                       // 改编来源（可选，便于追溯）
    code,                               // 有 bug 的代码
    tests: [{ expr, expect, tol }],      // 每条测试：Python 表达式 + 期望值 + 数值容差
    bugLines: [3],                      // 可接受的出错行（多数题只有 1 行）
    fixes: [{ line, replace, cheat? }],  // 候选修复：替换某一行；cheat=true 表示「改测试」类作弊选项
    answer,                             // 正确修复下标
  }
  ```
  测试的「实际值」不写在题库里，由构建期生成（见下）。
- **构建期校验与预计算**：一个脚本（与 verify-quiz 同一 python 探测逻辑、UTF-8 输出）对每道找 bug 题：
  1. 运行有 bug 的代码，对每条测试求值，记录实际值——必须至少一条不符合期望；
  2. 应用正确修复，所有测试必须通过，记录修复后的实际值；
  3. 应用每个非作弊的错误修复，必须至少一条测试失败，记录失败测试与其实际值（用于答错反馈）；
  4. 作弊选项：校验其确实只改测试 / 期望而不改代码。
  结果写入入库的数据文件（实际值表），CI 重新生成并比对无差异。
- **两步判分**：定位错不扣心（记录尝试次数）；修复错按规则扣 1 心（最低 1 心，与四选一一致）；规则待 01 号 grilling 确认。
- **槽位与题池**（推荐，待 01 号 grilling）：第十章「验证回廊」（巢穴）新增 1 块「找 bug 符文」，独立题池（如 `w10debug`），
  tier 取第十章巢穴档；v1 为祝福符文形态（答对回心），不改变 BOSS 战流程。后续可考虑让幻言魔像的 BOSS 符文以找 bug 形态出现。
- **呈现**：代码按行渲染（与 code-trace-replay 的「按行渲染代码块」prefactor 共用），可点击行；
  测试表三列「测试 / 期望 / 实际」，✓ / ✗ 带文字；修复候选以「第 N 行 → 新代码」的 diff 样式展示。
- **与 vibe-coding-dialogue 的分工**：对话符文练「和 AI 协作的流程」（选 prompt、选测试、决定接受与否），
  找 bug 符文练「读测试结果定位与修复」。两者都用第十章情景，01 号 grilling 时要避免同一个 bug 情景在两种题型里重复。
- **术语**：GLOSSARY 新增「找 bug 符文」「测试表」「作弊修复」。

## 测试决策

- 好测试只看玩家可见结果：测试表显示正确、定位 / 修复两步交互可完成、错误修复的反馈显示正确的失败测试、奖励到账。
- **E2E（首选）**：runner 新增步骤 `debugRune`：打开找 bug 符文 → 先点一行错误的行，断言提示出现且心数不变 →
  点接缝给出的正确行 → 先选一个错误修复，断言扣 1 心且显示失败测试 → 再选正确修复，断言测试表全绿、奖励到账。
- **接缝**：`__PYQUEST__` 只读查询 `debugRune()` 返回 { step, bugLines, answer }（测试用，不提供直接判对的动作）。
- **构建期校验（CI）**：四条规则（见实现决策）全部满足；重新生成无差异；用一个不进游戏的夹具题演示每条规则能抓到违规
  （例如「错误修复其实也能让测试全过」时校验失败）。
- **smoke**：数据字段完整、`bugLines` 在代码行范围内、`answer` 下标合法、题池 tier 一致、kind 已注册。

## 待决策

1. **定位错是否扣心？** 推荐不扣（定位是推理过程，鼓励尝试），修复错扣 1 心。
2. **槽位形态**：推荐第十章巢穴 1 块独立找 bug 符文（祝福符文形态）；备选：替换一块现有祝福符文。
3. **首批改编哪些题？** 推荐 vc11（漏归一化）、vc12（角度当弧度）、vc13（bin 边界 off-by-one）、vc15（除零污染）、vc16（math 遇数组）
   五个情景，由 01 号起草改编稿、助教确认；vc14（锚点测试）的思想直接体现在测试表设计里。
4. **作弊选项是否每题都有？** 推荐每题恰好一个，形式多样（改期望值 / 删掉失败的测试 / 放宽容差）。
5. **第一章到第三章是否也做？** 新手常见 bug（range 边界、`=` 与 `==`、缩进、字符串与数字相加）很适合，
   但属于新内容，推荐第十章样板验证后再走提纲（05 号）。

## 不做的事

- v1 不在浏览器里运行 Python（测试结果全部构建期预计算）；不支持自由编辑代码。
- 不做多行 / 多处 bug 的修复（每题一处 bug、一行修复）。
- 不改现有 W10 四选一题的任何内容；找 bug 题是新增的改编题，走 grilling。
